# Code Review: Redux Store & RTK Query Setup — Khajna Watch Frontend

## Summary
The overall RTK Query architecture is sound — single `baseApi` with `injectEndpoints` per domain, consistent tag-based invalidation, and a shared response-unwrapping layer. But there are two live correctness bugs (one causes incorrect search results, one is a real crash risk on first render), one bug that spams failed requests for every logged-out visitor indefinitely, a data-loss bug where a UUID gets shown as a person's name, and a meaningful amount of duplicated pagination boilerplate across four files that should be a single shared type/helper.

## Critical Issues

| # | File | Line | Issue | Severity |
|---|------|------|-------|----------|
| 1 | `redux/api/baseApi.ts` | ~70 | `unwrappingBaseQuery`'s error fallback: `(payload && "message" in payload) \|\| "Request failed"` — this is a boolean OR, not a value lookup. When the backend sends a top-level `message` field, this evaluates to the **boolean `true`**, not the actual string, so `err.message` shows up as `true` instead of the real error text anywhere a component does `toast.error(err.message)`. | 🔴 Critical |
| 2 | `app/reports/page.tsx` | 29–39 | Server-side pagination (`useGetReportsQuery({page, limit: 10})`, only 10 reports fetched) is piped into `getReports({q, reason, status, sort}, reports, plots)`, which filters/sorts **client-side**. Typing a search query only searches the current page's 10 reports — a user on page 2 searching for something on page 5 gets zero results even though it exists. Server-side pagination and client-side filtering are incompatible without also sending `q`/`reason`/`status` to the backend. | 🔴 Critical |
| 3 | `app/reports/page.tsx` | 160–161 | `page={meta?.page as number}` / `totalPages={meta?.totalPages as number}` — `meta` is genuinely `undefined` during initial load, but these `as number` casts lie to TypeScript. `Pagination`'s guard is `if (totalPages <= 1) return null`, and in JS `undefined <= 1` is `false` — so the guard doesn't fire, and `getPageRange` runs arithmetic on `undefined`, which can throw or render garbage on first paint. | 🔴 Critical |
| 4 | `components/notifications-menu.tsx` (rendered from `components/shell.tsx:104`) | 29–34 | `NotificationsMenu` is rendered **unconditionally** in the header for every visitor. `useGetNotificationsQuery` polls every 30s, but `/notifications` requires a logged-in session — every anonymous visitor generates a failing request every 30 seconds, forever, for as long as the tab stays open. Needs `{ skip: !user }` (or gate the whole component behind login state). | 🔴 Critical |
| 5 | `reportSelectors.ts` | `reporterName: report.reporterUserId ?? ""` | `ReportSummaryApi` has no display-name field — only `reporterUserId` (a raw UUID). This line silently aliases the UUID as the "name." `ReportCard`'s anonymity fallback (`report.isAnonymous \|\| !report.reporterName ? t.reportAnon : report.reporterName`) never catches this for non-anonymous reports, since the UUID string is always truthy — **real users' names render as raw UUIDs in the UI.** | 🔴 Critical |

## Suggestions

| # | File | Line | Suggestion | Category |
|---|------|------|------------|----------|
| 1 | `plotApi.ts`, `reportApi.ts`, `notificationApi.ts`, `watchlistApi.ts` | multiple | The exact same `{ page, limit, total, totalPages }` pagination shape is independently redeclared in **four** files (`PlotListResult`, `ReportListResult`, notification's `ListResult`, and implicitly in watchlist). Extract one shared `Pagination` / `Paginated<T>` type into e.g. `redux/api/types.ts` and import it everywhere. | Maintainability |
| 2 | `plotApi.ts`, `reportApi.ts`, `notificationApi.ts` | multiple | The `const m = meta as unknown as {...}` cast is copy-pasted in three separate `transformResponse` implementations. Extract a shared helper in `baseApi.ts`, e.g. `getPaginationMeta<M>(meta): M`, so the cast pattern exists in exactly one place. | Maintainability |
| 3 | `reportSelectors.ts` | `basePlot` construction | Hardcodes `landClass: ""`, `landClassBn: ""`, `surveyType: ""`, `possession: "matches"`, `khajnaStatus: "unknown"`, `khajnaYear: null`, `flagCount: 0` — but `PlotSummaryApi` actually has `plot.landClass`, `plot.surveyType`, `plot.possession`, `plot.khajnaStatus`, `plot.khajnaYear`, and `plot._count.flags` available right now. This looks like leftover code from before `PlotSummaryApi` was expanded (the comment `// added:` in `plotApi.ts` marks exactly these fields as later additions). Every report card is silently showing blank/wrong plot metadata that's already sitting in the fetched data. | Correctness |
| 4 | `redux/watchlist/watchlistSlice.ts`, `store/index.ts`, `providers.tsx` | whole file | Confirmed via project-wide grep: **zero** components reference `watchlist.codes` or `toggleWatch` anymore — every real caller was migrated to the backend-driven `watchlistApi` earlier. This slice is 100% dead: still registered in the store, still hydrated from `localStorage` on load, still written to `localStorage` on every dispatch. Safe to delete along with its `hydrate`/`toggleWatch` actions and the corresponding lines in `providers.tsx`. | Dead code |
| 5 | `redux/providers.tsx` | `store.subscribe(...)` | This subscriber fires on **every single store dispatch app-wide** — including every RTK Query internal `pending`/`fulfilled`/`rejected` action, not just watchlist/lang changes — and does two unconditional synchronous `localStorage` writes each time. On a page doing several queries, that's several redundant localStorage writes per second, none of which actually changed. Compare the relevant slices before writing, or scope the subscription with a selector. | Performance |
| 6 | `watchlistApi.ts` | comment above `getMyWatchlist` | Comment says *"Logged-in users only — the backend requires a real account for this one"* — this is stale; that endpoint was specifically opened up to anonymous identities. Misleading for the next person who reads it. | Documentation |
| 7 | `reportApi.ts` | `ReportSummaryApi.myVote: string` | Backend genuinely returns `null` when the user hasn't voted (`votes[0]?.vote ?? null`). The type says non-nullable `string`. Should be `myVote: "yes" \| "no" \| null`. Works today because comparisons like `!== "no"` happen to behave correctly against `null`, but it's a landmine for any future code that assumes it's always a string. | Type safety |
| 8 | `authApi.ts` | `register` mutation | `login` dispatches `setUser` and invalidates `"Auth"` on success; `register` does neither. If registration also logs the user in server-side (sets a session cookie), the UI won't reflect it until something else triggers a refetch. Worth confirming this is intentional. | Correctness (unverified — depends on backend register behavior) |
| 9 | `plotApi.ts` | `getPlots` vs `searchPlots` | Both hit the same `/plots` URL with different query shapes but are registered as fully separate endpoints — no cache is shared between "give me everything" and "give me page 2 filtered." Reasonable given they serve genuinely different needs, but worth documenting explicitly as a deliberate trade-off rather than an oversight, since a future reviewer could easily "fix" this into a bug. | Architecture (informational) |

## What Looks Good
- One `baseApi` with `injectEndpoints` per domain file — correct RTK Query pattern, single middleware/reducer registration, no duplicate `createApi` instances.
- `unwrappingBaseQuery` centralizes envelope-unwrapping (`{success, data, meta}` → `data`) so individual endpoints don't repeat that boilerplate — the one bug found here (#1 above) is in a rarely-hit branch, not the core design.
- Tag-based invalidation is used correctly and consistently for the mutations that matter (`createReport`, `voteReport`, `addToWatchlist`/`removeFromWatchlist`, `markNotificationRead`) — per-item tags plus a `"LIST"` tag is the right pattern throughout.
- `getReports`'s handling of two genuinely different backend response shapes (bare array vs. `{items, pagination}`) via one `transformResponse` is a clever, well-commented solution to a real API inconsistency, not a hack.
- `x-anon-id` threaded through `prepareHeaders` centrally means every endpoint automatically supports anonymous identity without each one repeating that logic.

## Verdict
**Request Changes.** Items #2 and #4 under Critical are user-facing functional bugs (broken search, permanent failing background requests for anonymous users), and #5 is a real privacy/trust issue (showing a UUID where a person's name should be). None of these are architectural rewrites — they're each a small, contained fix — but they should land before this ships further.
